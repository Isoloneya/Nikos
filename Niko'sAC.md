# Технічне завдання проєкту Niko's

**Технологічний стек:** TypeScript, Next.js (App Router), Prisma, PostgreSQL, Tailwind CSS

---

## AC-01. Опис та постановка задачі

### Назва проєкту

Niko's

### Предметна область

Веб-застосунок для мережі ресторанів Pan-Asian кухні — універсальний сайт, що обслуговує одразу всі філії мережі, з переглядом меню, онлайн-замовленням, бронюванням столика та адмініструванням контенту.

### Проблема

Мережа ресторанів з десятками філій по країні стикається з тим, що меню, ціни та доступність страв відрізняються між локаціями, а окремого сайту на кожну філію ніхто не підтримує. Клієнту незручно щоразу телефонувати чи шукати актуальну інформацію вручну, а власники мережі не мають єдиного місця для керування контентом, бронюваннями та замовленнями без залучення розробника на кожну зміну.

### Цільова аудиторія

- клієнти мережі, що обирають страви, оформлюють доставку/самовивіз або бронюють столик у конкретній філії;
- адміністратори мережі, які керують меню, локаціями, бронюваннями та статусами замовлень.

### Призначення системи

Система дозволяє клієнту обрати локацію один раз, після чого меню, кошик, бронювання й замовлення автоматично прив'язуються саме до неї. Адміністратор керує повним циклом контенту й операційних даних через окрему захищену панель без втручання в код.

### Основні сценарії використання

1. Реєстрація та автентифікація клієнта в системі.
2. Вибір локації (філії), меню якої відображатиметься клієнту.
3. Перегляд меню з фільтрацією за гостротою, дієтою (vegan) та пошуком за назвою/описом страви.
4. Додавання страв у кошик, зміна кількості, видалення позицій.
5. Оформлення замовлення: доставка (лише онлайн-оплата) або самовивіз (онлайн наперед чи оплата на місці).
6. Отримання email-підтвердження замовлення та відстеження його статусу в особистому кабінеті.
7. Бронювання столика з підтвердженням на email.
8. Керування адміністратором стравами меню, локаціями та статусами бронювань і замовлень через окрему адмін-панель.

### Перелік ключових функцій

- реєстрація та автентифікація клієнтів (сесія на JWT, httpOnly cookie);
- окрема автентифікація адміністраторів (ізольована від клієнтської);
- перегляд меню з прив'язкою до обраної локації;
- пошук і фільтрація страв (гострота, vegan);
- кошик, що зберігається протягом сесії браузера;
- оформлення замовлення з розгалуженою логікою оплати залежно від способу отримання;
- історія замовлень та відстеження статусу виконання;
- бронювання столика;
- email-сповіщення про бронювання та замовлення;
- адмін-панель: CRUD страв меню та локацій, перегляд і зміна статусу бронювань і замовлень.

## AC-02. Архітектура та структура системи

### Загальний підхід

Використовується Next.js App Router, що поєднує серверний рендеринг сторінок (React Server Components) і backend-логіку (Route Handlers) в межах одного застосунку та одного деплою, без окремого клієнт-серверного розділення на рівні хостингу.

### Компоненти системи

**Сторінки (Server Components).** Розташовані в `app/`, виконують запити до бази даних напряму через Prisma під час серверного рендерингу і передають готові дані в клієнтські компоненти. Відповідають за початкове завантаження контенту (SEO, швидкість першого рендеру).

**Клієнтські компоненти.** Позначені директивою `"use client"`, відповідають за інтерактивність: стан форм, кошик (через React Context), фільтри меню, модальні дії. Взаємодіють із сервером через `fetch` до Route Handlers.

**Route Handlers (API).** Розташовані в `app/api/**/route.ts`, приймають HTTP-запити, виконують валідацію вхідних даних, бізнес-логіку (перевірку прав доступу, розрахунок суми замовлення, формування email) та звернення до бази через Prisma.

**База даних.** PostgreSQL (хостинг — Neon), доступ через Prisma ORM з єдиним синглтон-клієнтом (`lib/prisma.ts`), що запобігає створенню зайвих з'єднань під час hot-reload у розробці.

### Обґрунтування архітектурних рішень

- Next.js App Router обрано замість окремих frontend/backend-застосунків, оскільки серверні компоненти дозволяють уникнути зайвого шару REST-запитів для початкового рендеру сторінок, а Route Handlers покривають потребу в API там, де потрібна інтерактивність (форми, кошик, адмін-дії).
- На відміну від класичної тришарової моделі (Router → Service → Repository), у Route Handlers валідація, бізнес-логіка та звернення до Prisma об'єднані в межах одного файлу-обробника. Це свідоме спрощення: для обсягу проєкту повноцінний Service/Repository-шар додав би непотрібну непрямоту без приросту гнучкості, оскільки Prisma сама виконує роль типобезпечного шару доступу до даних.
- Кошик реалізовано через React Context (`CartContext`), а не через сервер чи БД, оскільки для незареєстрованого відвідувача це прийнятний компроміс швидкості розробки; втрата кошика при перезавантаженні сторінки — усвідомлений недолік MVP.
- Автентифікація клієнтів і адміністраторів розділена на дві незалежні системи (окремі cookie, окремі JWT, окремі таблиці `User`/`AdminUser`), щоб компрометація клієнтської сесії не давала доступу до адміністративних функцій.

### Наскрізний потік запиту (приклад: оформлення замовлення)

Клієнт заповнює форму на `/checkout` → клієнтський компонент відправляє `POST /api/orders` з даними кошика → Route Handler перевіряє обов'язкові поля та наявність адреси для доставки → визначає поточного користувача через сесійний cookie (якщо є) → створює замовлення й пов'язані позиції через Prisma → надсилає email-підтвердження через Resend → повертає створене замовлення → клієнт очищує кошик і перенаправляється на головну.

### Навігація

Верхня панель (`Header`) присутня на всіх клієнтських сторінках і містить: логотип, пошук, посилання на інформаційні сторінки, поточну обрану локацію, посилання на профіль (або "Увійти" для неавтентифікованого користувача) і кошик із живою сумою. Адмін-панель має власну бічну навігацію (`AdminDashboardLayout`) з розділами Меню / Локації / Бронювання / Замовлення, повністю ізольовану від публічної навігації сайту.

### Форми введення

| Форма | Поля |
|---|---|
| Реєстрація | ім'я, email, телефон (опційно), пароль |
| Логін | email, пароль |
| Бронювання | ім'я, телефон, email, дата, час, кількість гостей, локація, коментар (опційно) |
| Оформлення замовлення | спосіб отримання, локація, адреса (для доставки), ім'я, телефон, email, спосіб оплати, коментар |
| Адмін: страва меню | назва, опис, ціна, фото (URL), категорія, ознаки гостроти/vegan/доступності, прив'язка до локацій |
| Адмін: локація | назва закладу, місто, адреса, телефон, години роботи, email для бронювань, активність |

Форми клієнтської частини проходять валідацію обов'язкових полів на стороні браузера (атрибут `required`, типи `email`/`date`/`time`) та повторну перевірку на сервері в Route Handler перед записом у базу.

### Відображення даних

Меню відображається картками страв (фото, назва, опис, ціна, бейджі "Гостре"/"Vegan") у сітці, що адаптується під ширину екрана. Статус замовлення на сторінці деталей відображається як горизонтальний таймлайн із чотирма кроками (Нове → Готується → В дорозі → Доставлено). Для порожніх станів (порожній кошик, відсутність замовлень) передбачені інформаційні заглушки із закликом до дії (перейти в меню).

### Повідомлення користувачу

Помилки форм (невдала реєстрація, неприйняте бронювання) відображаються інлайново під формою текстом акцентного кольору. Успішне бронювання показує окремий екран підтвердження замість форми. Кнопки дій під час відправки запиту переходять у стан очікування (зміна тексту на "Надсилаємо...", блокування повторного натискання).

### Адаптивність

Інтерфейс адаптується під мобільні пристрої та десктоп за допомогою брейкпоінтів Tailwind CSS: навігація на мобільних згортається в бічне меню за кнопкою-гамбургером, сітка карток страв змінює кількість колонок залежно від ширини екрана, бічна панель фільтрів на сторінці меню на мобільних прихована за кнопкою "Фільтри".

## AC-04. Робота з даними

### Перелік сутностей

| Сутність | Опис | Основні поля |
|---|---|---|
| Restaurant | філія мережі | id, name, city, address, phone, workingHours, bookingEmail, isActive |
| Category | категорія меню | id, name, order |
| MenuItem | страва меню | id, name, description, priceCents, photoUrl, isSpicy, isVegan, isAvailable, categoryId |
| User | обліковий запис клієнта | id, email (унікальне), passwordHash, name, phone |
| AdminUser | обліковий запис адміністратора | id, email (унікальне), passwordHash |
| Order | замовлення | id, type, address, paymentMethod, status, totalCents, contactName, contactPhone, restaurantId, userId |
| OrderItem | позиція замовлення | id, quantity, priceAtOrder, orderId, menuItemId |
| Booking | бронювання столика | id, name, phone, email, date, time, guests, status, restaurantId |

### Обмеження цілісності даних

- поле `email` унікальне для `User` та окремо для `AdminUser`;
- `MenuItem` пов'язаний з `Restaurant` через зв'язок many-to-many (одна страва може бути доступна в кількох філіях, а не в усіх одразу);
- ціни зберігаються в копійках (`priceCents: Int`), а не в грошових одиницях із плаваючою комою, щоб уникнути похибок округлення;
- `OrderItem.priceAtOrder` фіксує ціну на момент замовлення окремо від поточної `MenuItem.priceCents`, тому зміна ціни в адмінці не змінює заднім числом суму вже оформлених замовлень;
- видалення `Order` каскадно видаляє пов'язані `OrderItem` (`onDelete: Cascade`);
- `Order.userId` є опційним — замовлення можна оформити без реєстрації (гостьовий чекаут), у такому разі воно не потрапляє в історію замовлень жодного акаунта.

### Операції над сутностями

| Сутність | Створення | Читання | Оновлення | Видалення |
|---|---|---|---|---|
| Restaurant | адмінка | публічно (активні), адмінка (усі) | адмінка | адмінка |
| MenuItem | адмінка | публічно (доступні, за локацією) | адмінка | адмінка |
| User | публічна реєстрація | власний профіль | — (не реалізовано) | — (не реалізовано) |
| Order | клієнт (чекаут) | власник замовлення, адмінка (усі) | адмінка (лише статус) | — |
| Booking | клієнт (форма бронювання) | адмінка (усі) | адмінка (лише статус) | — |

## AC-05. Форми та валідація

### Рівні валідації

1. **Клієнтська валідація** — атрибути `required`, `type="email"`, `type="date"`, `min` для кількості гостей; покращує взаємодію, але не є механізмом захисту даних.
2. **Валідація на рівні Route Handler** — перевірка обов'язкових полів і бізнес-умов (наприклад, обов'язковість адреси для доставки) безпосередньо в обробнику запиту перед зверненням до Prisma.
3. **Валідація на рівні бази даних** — обмеження унікальності (`@unique` на email), типізовані enum-поля (`OrderStatus`, `PaymentMethod`, `BookingStatus`), що унеможливлюють запис некоректного значення.

### Правила валідації за формами

| Поле | Правило | Рівень валідації |
|---|---|---|
| email (реєстрація) | коректний формат, обов'язкове поле | клієнт |
| email (реєстрація) | унікальність у системі | Route Handler |
| password | мінімум 6 символів | клієнт |
| бронювання: дата/час/гості | обов'язкові поля | клієнт, Route Handler |
| бронювання: локація | наявність у базі | Route Handler |
| чекаут: адреса | обов'язкова лише за типом "доставка" | Route Handler |
| чекаут: кошик | не може бути порожнім | Route Handler |
| адмінка: ціна страви | ціле число (копійки) | Route Handler |

### Відображення результатів валідації

Помилки Route Handler повертаються у форматі `{ error: string }` з відповідним HTTP-кодом (400 для невалідних даних, 401 для відсутньої автентифікації, 409 для конфлікту — наприклад, email, що вже зареєстрований). Клієнтський компонент відображає отримане повідомлення текстом під формою без додаткового парсингу.

## AC-06. Взаємодія frontend і backend

### Механізм взаємодії

Взаємодія відбувається двома шляхами: (1) прямі виклики Prisma із серверних компонентів під час рендеру сторінки — без проміжного HTTP-запиту; (2) `fetch`-запити з клієнтських компонентів до Route Handlers у форматі JSON — для дій, що змінюють стан (реєстрація, оформлення замовлення, зміна статусу в адмінці).

### Автентифікація на рівні транспорту

Після успішного входу сервер видає JWT (підписаний бібліотекою `jose`), який зберігається в httpOnly cookie (`session` для клієнтів, `admin_session` для адміністраторів) — недоступний для читання з JavaScript на клієнті, що знижує ризик крадіжки токена через XSS. Кожен захищений Route Handler і серверний компонент отримує поточного користувача через `getCurrentUser()` / `getCurrentAdmin()`, які читають і перевіряють токен із cookie на сервері.

### Структура API

```
Auth (клієнти):   POST /api/auth/register
                  POST /api/auth/login
                  POST /api/auth/logout

Auth (адмін):     POST /api/admin/login
                  POST /api/admin/logout

Orders:           POST /api/orders
                  GET  /api/orders

Bookings:         POST /api/bookings

Location:         POST /api/location

Admin: Menu:      GET    /api/admin/menu-items
                  POST   /api/admin/menu-items
                  PATCH  /api/admin/menu-items/{id}
                  DELETE /api/admin/menu-items/{id}

Admin: Restaurants: GET    /api/admin/restaurants
                    POST   /api/admin/restaurants
                    PATCH  /api/admin/restaurants/{id}
                    DELETE /api/admin/restaurants/{id}

Admin: Bookings:  PATCH /api/admin/bookings/{id}

Admin: Orders:    PATCH /api/admin/orders/{id}
```

### Формат обробки помилок

Помилки повертаються у вигляді:

```json
{ "error": "Заповніть усі обов'язкові поля" }
```

| Код HTTP | Умова виникнення |
|---|---|
| 400 | порушення бізнес-правила / відсутні обов'язкові поля |
| 401 | відсутня або недійсна автентифікація |
| 404 | ресурс не знайдено (наприклад, чуже замовлення) |
| 409 | конфлікт даних (email вже зареєстрований) |

### Формат успішної відповіді

Одиничний ресурс повертається безпосередньо в тілі відповіді (наприклад, створене замовлення або оновлена страва меню) без обгортки чи пагінації — обсяг даних у проєкті не потребує пагінації списків.

### Розподіл відповідальності між шарами

| Шар | Відповідальність | Заборонено |
|---|---|---|
| Server Component (`page.tsx`) | серверний запит даних через Prisma, передача пропсів у клієнтський компонент | зберігання інтерактивного стану (`useState`) |
| Client Component | форми, стан кошика/фільтрів, виклики `fetch` до Route Handlers | прямі запити до Prisma |
| Route Handler | приймання HTTP-запиту, валідація, бізнес-логіка, звернення до Prisma, відправка email | рендеринг UI |
| `lib/*` | перевикористовувані утиліти (автентифікація, форматування, синглтон Prisma-клієнта) | HTTP-специфічна логіка |

### Уникнення дублювання коду

Перевірка поточного користувача винесена в єдині функції `getCurrentUser()` і `getCurrentAdmin()`, що використовуються і в серверних компонентах (для `redirect`), і в Route Handlers (для авторизації дій). Логіка відправки email централізована в `lib/email.ts` (`sendBookingConfirmation`, `sendOrderConfirmation`) і викликається лише з відповідних Route Handlers. Форматування ціни з копійок у гривні винесене в єдину функцію `formatPrice()`.

### Угоди щодо іменування

Компоненти та файли сторінок іменуються у `PascalCase`/`kebab-case` відповідно до конвенцій Next.js App Router (`page.tsx`, `layout.tsx` — зарезервовані імена файлів-маршрутів). Типи та Prisma-моделі іменуються іменниками в однині (`Order`, `Restaurant`). Функції-утиліти іменуються дієсловами, що відображають дію (`getCurrentUser`, `formatPrice`, `sendOrderConfirmation`).

### Обґрунтування рівня складності архітектури

Окремий Service/Repository-шар, чергу повідомлень чи мікросервісну декомпозицію свідомо не застосовано — для обсягу проєкту (одна мережа, одна база даних, без високого навантаження) вони становили б надлишкову складність без приросту якості чи гнучкості.

## AC-11. Безпека

| Загроза | Захід протидії |
|---|---|
| SQL-ін'єкція | використання Prisma ORM із параметризованими запитами; відсутність "сирих" SQL-запитів |
| Небезпечне зберігання паролів | хешування паролів bcrypt (`bcryptjs`); у базі зберігається лише `passwordHash` |
| Витік секретів | зберігання конфіденційних параметрів у змінних середовища Vercel, відсутність секретів у репозиторії |

## AC-12. Автентифікація та авторизація

### Автентифікація

Реалізована через JWT (бібліотека `jose`): після реєстрації або входу сервер видає підписаний токен, що зберігається в httpOnly cookie. Кожен запит, що потребує ідентифікації користувача, звіряє токен на сервері через `verifySessionToken()`.

### Модель авторизації

Дві незалежні ролі на рівні застосунку: **клієнт** (доступ до власного профілю, історії замовлень, оформлення замовлень і бронювань) і **адміністратор** (доступ виключно до `/admin/dashboard/*` і відповідних `/api/admin/*` маршрутів). Проміжної рольової моделі в межах клієнтських акаунтів не передбачено — усі зареєстровані клієнти мають однакові права.

### Матриця прав доступу

| Дія | Гість | Клієнт | Адміністратор |
|---|---|---|---|
| Перегляд меню, локацій | так | так | так |
| Оформлення замовлення (гостьове) | так | так | — |
| Перегляд власної історії замовлень | ні | так | — |
| Перегляд усіх замовлень/бронювань | ні | ні | так |
| Зміна статусу замовлення/бронювання | ні | ні | так |
| CRUD страв меню та локацій | ні | ні | так |

Перевірка доступу до адмін-розділу централізована в `app/admin/dashboard/layout.tsx`, що виконує `redirect("/admin/login")` за відсутності дійсної адмін-сесії ще до рендеру будь-якої дочірньої сторінки — унеможливлює дублювання перевірки в кожному окремому маршруті.

## AC-13. Обробка помилок

Обробка помилок реалізована на трьох рівнях:

1. **Очікувані помилки бізнес-логіки** (відсутні обов'язкові поля, email вже зайнятий, невірний пароль) повертаються Route Handler у вигляді `{ error: string }` з відповідним HTTP-кодом; клієнтський компонент відображає текст помилки безпосередньо під формою.
2. **Помилки зовнішніх інтеграцій** (відправка email через Resend) обгорнуті в `try/catch` і не блокують основну операцію — якщо лист не надіслався, замовлення чи бронювання все одно успішно створюється в базі, а помилка лише логується на сервері (`console.error`), щоб клієнт не втратив реальне замовлення через збій стороннього сервісу.
3. **Непередбачені помилки** (збій з'єднання з базою даних) обробляються стандартним механізмом обробки помилок Next.js — користувачу показується узагальнена сторінка помилки без розкриття технічних деталей.

## AC-14. Розгортання

### Локальний запуск

Детальна інструкція наведена в `README.md`: встановлення залежностей (`npm install`), налаштування змінних середовища, застосування міграцій (`npx prisma migrate dev`), заповнення бази тестовими даними (`npx prisma db seed`), запуск сервера розробки (`npm run dev`).

### Розгортання на хостингу

Застосунок розгорнутий на **Vercel** із автоматичним деплоєм при пуші в гілку `main`. Vercel самостійно розпізнає Next.js-проєкт і налаштовує білд без додаткової конфігурації; скрипт `postinstall: prisma generate` гарантує генерацію Prisma Client перед кожним білдом.

### Підготовка бази даних при розгортанні

Продакшн-база — PostgreSQL на **Neon**, підключення передається через змінну середовища `DATABASE_URL`, задану в Vercel Environment Variables. Перед першим запуском на новому середовищі виконується `npx prisma migrate deploy` для застосування схеми.

### Можливі вдосконалення

Верифікація власного домену в Resend (наразі листи надсилаються з `onboarding@resend.dev`, що підвищує ризик потрапляння в спам), реалізація повноцінної онлайн-оплати через платіжний провайдер (LiqPay/Fondy) та розширення рівнів гостроти страв з булевого поля до enum є доцільними напрямками розвитку проєкту понад поточний обсяг MVP.
